# ST0 双方持久舰船入战与结果关联

日期：2026-09-12。状态：`ST0_SCOPED_PASS / ST1_NEXT`。基线为 `d6d9221` 与 OP1 工作区改动。本片交付后台合同、双方装配、桌面桥接和存档关联；战略地图及正式遭遇界面尚未实现。

## 实现范围

新增 `tactical.realtime.deploy_encounter`，双方都必须提供已保存舰船，缺少对手记录直接拒绝。共用已提取的 `prepared_deployment.load_ship`，载入真实设计、船壳/模块状态、局部装甲、货物、弹药、损管、火情和燃料状态。原战前准备入口继续显式使用技术测试敌舰，不自动切换产品流程。

新增 `tactical.realtime.encounter` 查询遭遇回执，保存遭遇身份、战略世界引用及修订、双方成员/旗舰、场内身份映射和入场记录摘要。舰艇状态仍由原 P3 表保存；没有第二套库存。

遭遇登记与全部舰船占用在同一个事务内完成，编译后再次检查原存档完整内容与修订。场景接入失败会撤销全部占用和遭遇登记；相同请求在活动场景中重试返回原场景。身份相同而内容不同不能替换原场景。

P3 结算暂存与保存边界检查遭遇关联，拒绝错误场景、缺少/多出参战舰及不一致的入场状态。仍沿用全舰原子保存和幂等提交。已经保存的历史结果可重复读取/提交，即使原舰艇已进入下一场也不会再次扣费。

只有持有进程租约的后台才能释放中断场景的占用。未形成持久结算的交战中断后恢复双方入场存档；旧进程未落库的临时战果不能在中断后补交。已经暂存的结算仍阻止舰船被重新准备，重启后继续保存。

所有新增编译、存档访问和关联校验仅在入战、查询恢复和结算边界执行，没有修改固定步飞行、炮击或燃料消费循环。

## 输入与回执

输入版本 `gaotian.tactical-encounter/st0-v1`，完整样例见[合同夹具](./fixtures/st0-encounter.json)。

| 字段 | 当前约束 |
| --- | --- |
| `encounter_id` | 每次入战尝试的稳定身份，和入战认领身份共用命名空间；已结束/中断的身份保留，不用于开始另一场。接入失败且未形成结算时可原样重试 |
| `world_id / world_revision` | 记录调用方的世界身份与非负整数修订；ST0 尚无战略世界仓库，不宣称已验证世界当前修订或舰队所有权 |
| `player_side_id` | 必须指向提供的一个阵营，以其旗舰确定直接控制舰，不依赖名单顺序 |
| `sides` | 恰好两个不同阵营和不同舰队，每方一位名单内旗舰，双方合计 2—16 舰；这个上限是当前接口边界，不是战略舰队规模规则 |
| `ships` | 稳定实例身份、已保存修订和部署位置；重复实例、缺失存档、旧修订、场内身份冲突及被占用舰拒绝 |
| `deployment` | 二维局部坐标 `x_m/y_m`、弧度朝向 `heading_rad`；高度沿用保存设计部署。以船壳外接圆作保守间隔检查，尚非正式三维部署/高度层规则 |

回执版本 `gaotian.encounter-receipt/st0-v1`。返回输入、显式 `instance_mapping`、场景身份与结算身份。状态为 `active`、`interrupted`、`pending_settlement` 或 `state_saved`。`world_application` 明确为 `not_implemented`；`state_saved` 只表示舰船结果已保存，不表示世界时间已恢复或战略战果已应用。

入战和查询可通过桌面宿主的战术桥接调用；入战要求战术视图且无旧场景冲突，双方舰艇仍须先经现有设计/准备接口创建合法存档。查询不驱动战斗时间。世界暂停、舰队归属授权、正式遭遇生成及返回位置由 ST1/ST3 继续接线。

- ST0 新增 9 项测试通过，包括严格输入、真实炮击往返、重复/旧版本/占用/错位部署、接入失败回滚、待保存恢复、错误场景/名单、第二舰保存失败、修订竞争和未结算中断。首轮 8 项通过后，针对新增中断限制和编译后竞争补跑 2 项，其中 1 项是原用例加强；不将重复运行算作新增数量。
- 原准备部署 7 项、结算/准备事务/实时服务 50 项相关回归通过，共 57 项。
- 新增 Rust 宿主到真实 Python 子进程的桥接测试 1 项通过，覆盖能力发现、双方入战、请求重试、回执查询、撤离保存和关闭。它不是原生窗口视觉验收。

完整实际战果、回执和下一场武器状态见[验证产物](../../artifacts/st0-encounter-v1/result.json)。测试只使用临时隔离仓库，没有变更玩家存档。
