# T3a 当前后台性能诊断与优化建议（2026-09-08）

本次只做代码审查、测量与进程内对照实验，未把实验优化接入产品，也未操作用户现有试航窗口。当前瓶颈主要是推进合同在热路径上的重复解析、资源验证和规范序列化，不是狭义位置/速度积分或界面快照生成。

## 测量方法

使用当前真实两舰 v7 试航资源、战术不耗油和现行试航推力。每次独立建立场景，12 步前进预热，随后测量 60 步：20 步前进、20 步前进加左转、20 步制动。计时范围为生产后台的 `advance_one()`，不含创建、命令接受/暂停、测试结果比对或 UI/IPC。每个实验跑两次，第二次颠倒模式顺序。

逐步比较完整场景、指挥状态、仲裁结果和完整单步结果的规范 SHA。所有四种路径的 60 步序列均一致；这只是该序列的等价证据，不替代失效输入、战损、资源变更、失联及存档回归。

18 步 cProfile 另测，用于定位函数与调用次数；分析器会增加开销，不用其耗时推算真实帧预算。数据见 `artifacts/t3a-performance/diagnostic.json`、`profile-functions.json` 和 `backend.prof`。工具为 `tools/profile_tactical_backend.py`。没有修改历史黄金。

## 实测结果

| 进程内实验 | 60 步耗时中位数 | 平均每步 | 相对现状减少耗时 |
| --- | ---: | ---: | ---: |
| 当前后台 | 2.831 秒 | 47.18 ms | — |
| 按能力内容缓存精确响应时间解析 | 2.550 秒 | 42.50 ms | 9.9% |
| 使用已有 trusted_prevalidated 绑定路径 | 2.582 秒 | 43.03 ms | 8.8% |
| 两项结合 | 2.274 秒 | 37.89 ms | 19.7% |

基线 P95 约 49.2—49.6 ms。约 97.1% 的非分析器计时处于仲裁/模拟整合调用，表现快照约 2.5%。真正实时需要小于 16.67 ms/步并留余量：当前约需 2.8 倍提速；两项实验组合后仍约需 2.3 倍，不能承诺仅接缓存即可实时。

## 热点及成因

以下为 18 步样本的调用链统计，累计耗时相互嵌套，不能直接相加。

| 热点 | 次数 | 定位 |
| --- | ---: | --- |
| canonical_sha256 / canonical_json | 各 6246，约 347 次/步 | 指纹计算调用链约占 profiled advance_one 累计时间的 38%；主要成本包括对象转字典和 JSON 序列化，不只是 SHA 算法 |
| _parse_exact_timing_capability | 5400，300 次/步 | 对不变的发动机能力重复转换 Decimal、核算两方向全部阶段的精确时间与可排程性 |
| 完整安全适配器 _validate_state | 288，16 次/步 | 重复执行 state.to_dict→parse、控制解析、执行器集合/时钟/排程与 governor 关系验证 |
| validate_committed_propulsion_time_state | 3456，192 次/步 | 每次又解析发动机状态与静态响应能力 |
| verify_derived_ship_snapshot_fingerprint | 54，3 次/步 | 每步仍物化大型设计快照并重算规范指纹；现有每步上下文缓存并未消除跨上下文重复 |
| validate_fully_governed_scene_context | 54，3 次/步 | 外层仲裁与核心入口重复验证步首，另一轮用于结果或后续状态；需区分同一边界与新边界，不能一律省略 |

完整推进开/收边界分别包含大量上述工作。相比之下，样本中的狭义 `integrate_actual_tactical_step` 累计不到 1%；无弹丸的 `advance_projectile_world` 与无事故持续毁伤也很小。这不能外推到实际交火负载。

另发现旧优化与新接线脱节：`prepare_tactical_scene_bindings()` 已在创建时生成预验证绑定，但直控适配调用统一场景时没有指定快速路径，因此仍走默认 strict。旧 T0 规划中“固定步不重算完整设计指纹”是旧路径的成果，当前 v7 Web 路径尚未达到，不能直接沿用历史性能结论。

## 建议落地顺序

### 1. 先做静态能力预编译和资源验证复用

响应时间、启动时间、阶段表属于静态能力。为每种精确能力预编译 `_ExactTimingCapability` 与必要的阶段偏移表，在资源初始化时验证；步内只按当前阶段、目标和起点查表。保持现有 Decimal/ceil 舍入和“每步最多跨一阶”语义，不换成浮点近似。本次内容缓存实验约省 10%；正式预编译可进一步避免实验缓存键自身的 JSON 开销，实际收益仍需实测。

接通已有预验证绑定路径，并让场景绑定与推进上下文共享同一份已验证静态资源。完整验证保留在外部输入、创建、资源替换、载入与重建边界。资源必须真正只读且由该场景拥有；仅 frozen dataclass 不足以证明其内部嵌套容器不可变。先证明冻结/失效规则，再减少跨步重算，不能直接把验证改为空函数。

### 2. 分开外部严格解析与内部类型化计算

外部 JSON、存档和跨进程输入继续严格 parse。核心内部使用已验证的类型化对象，保留动态关键不变量，但避免同一状态在一条调用链中反复 to_dict/parse。

开边界 S_n、已提交开边界、收边界 S_n+1 和影子状态需分别标识，不能只按步号缓存状态验证。资源引用、控制、引擎阶段、故障和 governor 任一不同都不能误用证明。先建立“此函数接收何种已验证对象”的明确入口，再逐处去重；现有公开严格入口继续可用。

### 3. 复用同一边界的指纹，收敛审计构造

同一不可变状态或场景边界的规范指纹只算一次，供仲裁绑定、结果来源与日志引用。梳理 SHA 调用链，先消除重复大对象序列化；保持原规范字节和历史 hash 不变。不要直接去掉 canonical_json 的缩进/排序，也不要用 Python hash() 替代 SHA。

把完整审计序列化与每步必须保存的执行回执分开；用于正确性的来源绑定和可靠事件仍按原顺序生成。表现详情可以按实际发送频率生成，但本次快照仅约 2.5%，不是首要收益点，且须保留当前“投影失败不提交该步”的原子性或显式定义新的失败语义。

### 4. 再优化无变化路径与数据布局

在前三项后重新画像，再考虑空命令、无弹丸、无事故、未到期引擎、成员和阶段不变的聚合等快速路径。它们仍须执行到期时间、持续效果和精确结果所需的逻辑。整舰结构/乘员载荷依赖速度、姿态和阻力，不能仅因车钟未变就跳过安全判断。集合、索引和临时字典可优先预编译或复用。

### 5. 以剩余热点决定是否引入本地计算模块

若清理重复工作后仍不足，再将具体数值热点批量化或移入 Rust 等本地实现。两艘舰简单分 Python 线程不等于获得两倍吞吐，跨进程拆分还会增加状态同步和确定性成本。当前不以重写整个后台、降低 60 Hz 或改变实际推力作为计算性能优化方案。

## 每一片的验证门

保持物理结果、事件顺序、车钟响应、安全限推、换向互锁、战术不耗油、暂停和回执语义。至少覆盖同序列逐步完整结果一致、能力内容/资源更换、损毁/断电/缺员/无燃料、失去直控、旧输入、缓存失效、重建/重载与异常退出。

测量分开记录原始计算、表现投影、IPC/UI、预热和观察器开销。短样本先选方向；两舰交火与较长稳态测量再决定实时验收。6/20/30 舰扩容矩阵及历史指纹阻塞项保持原状态，不用本次两个重复的微基准替代。
